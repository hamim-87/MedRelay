# MedRelay on IBM LinuxONE

End-to-end, locally-run prototype of **MedRelay**: a hybrid GenAI + machine-learning + evidence-graph system that finds clinical follow-up obligations in notes, tracks them as a **temporal evidence graph**
with deterministic workflow states, and forecasts which ones are likely to remain unresolved at their deadline — executed on an **IBM LinuxONE (s390x, big-endian) virtual machine**.

> **Read this first.** Synthetic / simulated data only. Follow-up outcomes are *simulated* from explicit event timelines; action labels are *weak (rule-proposed, silver)* — there are **0 human-reviewed gold labels**;
> obligation extraction is scored on a *developer-annotated* challenge set plus synthetic template documents. Nothing here is clinically validated. Alerts and recommendations are for **qualified human review only**.
> Unverified or censored obligations are never counted as failures.

## Quick start (on the s390x VM)
```bash
python3 -m venv --system-site-packages .venv          # scientific stack comes from apt (no s390x wheels for numpy/pandas/pyarrow); see requirements-s390x.txt
.venv/bin/pip install -r requirements-s390x.txt        # pydantic, llama-cpp-python (built with VXE), gguf, jupyterlab, pytest ...
.venv/bin/python scripts/fetch_models.py               # IBM Granite 4.0 GGUF models; convert to big-endian as in docs/linuxone_setup.md section 6
.venv/bin/python scripts/run_notebook.py --mode fast --reset   # clean-kernel run, development subset (~12 min on 2 vCPU)
.venv/bin/python scripts/run_notebook.py --mode full           # every record, full benchmark sizes (hours; needs more than 4 GB RAM headroom, see Limitations)
.venv/bin/python scripts/make_report.py                        # reports/final_report.md from results/
.venv/bin/python -m pytest -q tests                            # tests (the notebook test executes the notebook repeatedly)
```
Interactive use: run Jupyter on `127.0.0.1` and reach it through an SSH tunnel (`ssh -N -L 8888:127.0.0.1:8888 ...`); nothing is exposed publicly. The LLM runs in-process (llama.cpp), remote LLM backends are disabled.

## Design decisions worth knowing
* **The LLM never sets a workflow state.** It only *proposes* evidence-grounded obligation records (validated against a Pydantic schema; fields whose evidence span is not in the source note are rejected). States come from deterministic rules over documented events.
* **Evidence-aware states**: `pending`, `completed_with_evidence`, `overdue_without_verified_completion`, `unverified_insufficient_evidence`, `contradictory_evidence`, `censored_not_yet_assessable`. A task with no evidence is *unverified*, not *failed*; late evidence reconciles the state.
* **Event time vs ingest time**; duplicates and out-of-order deliveries are handled idempotently; the recovered state from the SQLite event log is identical to the live state.
* **Leakage control**: features use only events ingested before the assessment time; models are trained on train, tuned on validation, thresholds chosen on validation and applied once to test; patient-grouped bootstrap CIs; no tuning on test.
* **Baselines are strong on purpose**: A = deadline-only rule/reminders, B = independent-task ML, C = graph-enhanced ML. Early-warning comparisons are restricted to alerts raised with a minimum lead time before the deadline, because near the deadline a deadline-only rule is hard to beat.
* **Hardware claims are evidence-based**: NNPA presence (CPU flag, facility 165, `libzdnn`) is reported separately from use. Tree/linear models (scikit-learn, XGBoost) do *not* run on NNPA. Only a direct zDNN matmul device test is evidence of NNPA execution.

## Results
Measured by `scripts/run_notebook.py --mode fast --reset` (clean kernel, 56 code cells, 0 errors, 12.2 min) on the LinuxONE VM. Every number below is read from `reports/fast_run/results/`.
A full-size run (`--mode full`) was started but **stopped before it finished** (the 4 GB VM ran out of memory headroom), so no full-mode numbers are reported.
Fast mode = development subset: 60 test patients, 319 test obligations, 100 bootstrap resamples, 12 documents per extraction corpus. **All follow-up outcomes are simulated; there are 0 human-reviewed gold labels.**

### Data (after validation: all hard checks pass)
3,284 patients, 11,173 encounters, 24,296 obligations, 34,441 source events, 10,002 action examples (weak labels), 110,521 real appointments (no-show), graph 103,627 nodes / 223,925 edges.

### Experiment 3: early warning, alerts at least 24 h before the deadline (thresholds chosen on validation at recall target 0.7, applied to test)

| system | alerts | recall | precision | false-alert rate | median lead (h) |
|---|---|---|---|---|---|
| A deadline-only rule | 167 | 1.000 | 0.755 | 0.191 | 36 |
| A reminder at 24 h | 155 | 1.000 | 0.827 | 0.124 | 24 |
| B independent-task ML | 120 | 0.800 | 0.832 | 0.096 | 24 |
| C graph-enhanced ML | 108 | 0.743 | 0.867 | 0.067 | 72 |

Threshold-free max-score PR-AUC: A deadline-only 0.981, B 0.963, C 0.969. Paired bootstrap differences: C minus A -0.012 (95% CI -0.034 to +0.017), C minus B +0.006 (95% CI -0.015 to +0.027).
**Honest reading:** the graph model gives fewer false alerts and a longer median lead at the chosen operating point, but its overall ranking quality is not significantly better than independent-task ML, and a deadline-only rule is strong close to the deadline.

### Evidence-aware states vs a naive "no record = failed" rule
* State accuracy at the assessment time: engine 0.903 vs naive 0.884; 0.997 after late evidence reconciles.
* Recognition of truly unverified/censored tasks: engine 0.97 vs naive 0.00.
* Injected missing documentation (53 tasks done but undocumented): naive rule called 100% overdue; the engine confirmed 0% as overdue (all flagged unverified).
* Duplicates: 406 duplicate deliveries ignored; final states identical to a clean run (100%).

### LinuxONE evidence and benchmarks (same run)
* Platform: s390x, big-endian, z/VM 7.3.0, 2 vCPU, 4.2 GB RAM; vector facility (VXE2) and NNPA flag/facility 165 present; Docker/Podman not installed. llama.cpp built with `VXE = 1`; Granite GGUF models converted to big-endian.
* Local LLM: granite-4.0-350m-Q8_0, 9.2 tokens/s on 2 threads (generation requests are serialised).
* NNPA device test (zDNN 1.0.1, 1024^3 matmul): NNPA 0.49 ms (operation) / 1.15 ms (with data conversion) vs NumPy BLAS 410 ms and a naive C loop 844 ms; max abs error 0.045 (16-bit arithmetic). **The tree/linear risk models do not use the NNPA.**
* Event processing: 19,254 events/s (graph + states, in-memory); 354 to 470 events/s with calibrated ML risk scoring (SQLite WAL or in-memory). Throughput on this small shared VM varies between runs.
* Queue under offered load (multiples of the consumer's measured capacity): blocking backpressure at 2x loses no events (p99 queue latency 664 ms); a bounded queue of 200 sheds 37.5% at 2x and 65.4% at 4x.
* 100,000-event workload: **not run** (full mode was stopped).

## Limitations
* All follow-up outcomes are simulated; the numbers describe the generator, not clinical reality. There are no gold action labels, so action-classifier scores measure agreement with rules, not correctness.
* The extraction evaluation set was written by the developers (not independent) and is small; the 350M model alone is too weak for extraction. The 1B model was evaluated on a smaller sample because generation is ~5× slower on this VM.
* A deadline-only rule is a strong late-window baseline; the graph model's measured advantage is confined to what the tables above show, with confidence intervals.
* The no-show model uses real appointment attendance (not follow-up completion), is licensed CC-BY-NC-SA, and must not be used to deny or deprioritise care; demographic features can encode bias.
* The VM has 2 vCPU / ~4 GB RAM / no swap, so benchmarks reflect that size, not a production LinuxONE LPAR. A full-size (`--mode full`) run was started but stopped when the VM ran out of memory headroom (the end-to-end GenAI stage slowed to a crawl), so only fast-mode results are reported; the 100k-event benchmark was not run.
* Host-key fingerprints pinned for the VM must be compared by the user with the ones in the IBM console.
